# Handover Memo — 2026-06-01

## What happened

S-bot (previous session) investigated why A-bot was misbehaving — stuck in query loops, hallucinating conversation truncation, calling non-existent APIs, and failing to provide useful direction.

## Root cause found

**A-bot was operating without its behavioral soul.** The SQL query in `a_db_reader.read_soul_from_db()` only selected `role, domain, responsibility` from `agent_souls` — NOT the `content` column. The full 3183-character behavioral document was never loaded. Compare with S-bot's `s_db_reader.read_s_soul_from_db()` which correctly selects `content`.

This means every time A woke up, it received ~100 chars of stub data instead of its actual instructions (PDCA Check scope, communication rules, values, boundaries, self-evolution guidelines). No wonder A behaved stupidly.

## Fixes applied (3 files changed)

### 1. `src/a_db_reader.gleam` — Load soul `content` column
- **Before:** `SELECT role, domain, responsibility FROM agent_souls WHERE id_prefix = 'A'`
- **After:** `SELECT content FROM agent_souls WHERE id_prefix = 'A' AND is_active = true`
- Removed `soul_responsibility_decoder()`, added `content_decoder()` (same pattern as S-bot)

### 2. `src/a_prompt_builder.gleam` — Remove hardcoded identity prompt
- Removed `a_identity_prompt()` function and its hardcoded string: `"Your identity, role, and behavior are defined by your soul and jobs loaded from the database below. Follow them."`
- This was a lie — the soul below was amputated. Now that `content` is actually loaded, the hardcoded line is redundant and confusing.
- Removed the `|> add_component(soul_component(a_identity_prompt()))` call from `build_system_prompt`

### 3. `src/a_prompt_builder.gleam` — Fix conversation truncation direction
- **Before:** `string.slice(s, 0, max)` — showed oldest entries, cut off newest
- **After:** `string.slice(s, len - max, max)` — shows the most recent entries
- A can now see what just happened instead of ancient history

## Additional issue: A-bot silently absorbs tool results

During the review cycle, A repeatedly called `psypi-issues`, `psypi-tasks`, `psypi-autonomic-alerts` — got empty results — and **never reported any of it to S**. It just silently absorbed the results.

Expected behavior: When A calls tools during its Check phase and gets unexpected results (empty, errors, mismatches with Monitor reports), it should **use `pi.sendMessage()` to report those findings back to S immediately**, just like reporting a bug. Otherwise S has no visibility into what A discovered (or failed to discover).

This is because A is using the **monitor LLM session** (via `call_monitor()`), not direct Pi tool calls. A's tool usage happens inside the LLM context, and the LLM may not naturally report intermediate tool results. The final wake-up message from A is the LLM's interpretation, not a structured report of tool results.

Possible fixes:
- Add an A-job: "After inter-review, summarize tool results and send to S via pi.sendMessage()"
- Or add to A's soul: "Always report what you found during Check, especially when results are empty or unexpected"

## Additional observation: A-bot's tool invocation pattern

During the review cycle, A's conversation entries contained patterns like:

```
psypi-tasks
```

(with trailing spaces, no parameters). **Important clarification:** A doesn't call Pi tools directly. A calls `call_monitor()` which invokes the LLM. The LLM then decides whether to use tools. What A sees in `ctx_get_entries_json()` is the conversation history — S's messages, tool results, etc.

The `psypi-tasks    ` pattern in the conversation is likely:
1. **S's previous tool calls** showing up in the conversation history (not A calling tools)
2. Or **A's LLM outputting text that looks like a tool call** but is actually just text in the wake-up message

No inter-reviews were saved (`SELECT * FROM inter_reviews` returns empty), confirming A never successfully completed a review cycle.
