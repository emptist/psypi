## Discussion Notes: Extension Generator Redesign

### Point 1: Identity Tools — Session ID is Internal Only

**Decision**:
- Session ID is an **internal working variable** for identity management, never exposed as a tool
- Remove any tool that queries or displays session ID directly
- Keep `psypi-my-id` and `psypi-partner-id` — they call `get_resolved_identity(permanent, ...)` with different boolean flags:
  - `psypi-my-id` → `get_resolved_identity(false, ...)` → current/temporary agent
  - `psypi-partner-id` → `get_resolved_identity(true, ...)` → permanent/partner agent
- Session ID is only used inside the `getIdentity()` JS helper, not exposed to users

**Implications for generator**:
- No need for complex `PiIdentityNeed` type with variants like `MyIdentity`, `PartnerIdentity`, `BothIdentities`
- Identity tools simply call `get_resolved_identity(permanent_bool, sessionId, ...)` directly
- Result formatting is straightforward (no special identity handling needed)
- Generator becomes significantly simpler

---

### Point 2: Agent ID is Synchronous — No Await Needed

**Analysis of ID generation**:
- Agent ID generation is **simple, fast computation** - no long computation or waiting
- The old JS `AgentIdentity` class manages agent dynamics (including permanent monitor/partner)
- ID is generated by function, not cached - enables tracking agent activities via function calls
- Key principle: **Getting ID doesn't need await**, but subsequent work (DB updates) must be guaranteed

**Design implications**:
- `get_resolved_identity()` is a **synchronous function** - returns ID directly
- When an agent does important work: 1) Get ID (sync) → 2) Do actual work (may involve DB)
- No complex async preamble needed for identity handling
- Identity is just a regular function call, passed as parameter like any other arg

**Implications for generator**:
- Remove all async identity preamble logic
- Identity call is synchronous: `const agentId = get_resolved_identity(...)`
- Pass ID to Gleam function as regular parameter
- Much simpler generator code - identity is just another `PiCallArg`

---

### Point 3: Type Naming Must Be Clear — Use AgentIdentity

**Problem**:
- During TS→Gleam migration, AI inconsistently renamed types
- Now unclear what `Agent` type actually is
- Must use **`AgentIdentity` type** to enable activity tracking

**Required fix**:
- Define clear `AgentIdentity` type in Gleam
- Ensure all identity-related functions use this type
- No more ambiguous naming like just `Agent` or unnamed records

## Pi ExtensionAPI — The One Critical Contract

**Source**: `/opt/homebrew/lib/node_modules/@mariozechner/pi-coding-agent/docs/extensions.md`
**Repo**: `https://github.com/earendil-works/pi`
**Note**: Pi changed repo from mariozechner to earendil-works. Verify if npm package name also changed.

### The ONLY thing extension.js must get right

Pi's extension system has **one required contract**:

```javascript
// 1. Module MUST export default function receiving ExtensionAPI
export default function(pi) {

  // 2. Register tools via pi.registerTool() with exact shape:
  pi.registerTool({
    name: "tool-name",           // string - identifier
    label: "Display Name",       // optional string
    description: "What it does", // string - shown to LLM
    parameters: Type.Object({    // @sinclair/typebox schema
      param1: Type.String(),
      param2: Type.Optional(Type.String()),
    }),
    async execute(toolCallId, params, signal, onUpdate, ctx) {
      // toolCallId: string
      // params: object (validated against parameters schema)
      // signal: AbortSignal (cancellation)
      // onUpdate: function (stream progress)
      // ctx: ExtensionContext (ui, cwd, sessionManager, model, etc.)
      return {
        content: [{ type: "text", text: "result" }],
        details: {},  // optional metadata
      };
    },
  });
}
```

### What this means for the Gleam generator

The generator (`extension_generator.gleam`) has **one job**: produce valid JavaScript that matches this contract. Specifically:

| Generator responsibility | Must match                                                    |
| ------------------------ | ------------------------------------------------------------- |
| Export format            | `export default function(pi) { ... }`                         |
| Tool registration        | `pi.registerTool({ name, description, parameters, execute })` |
| Parameter schemas        | `Type.Object({ ... })` using `@sinclair/typebox`              |
| Execute signature        | `(toolCallId, params, signal, onUpdate, ctx)`                 |
| Return shape             | `{ content: [{ type, text }], details? }`                     |
| Error handling           | Try/catch wrapping each Gleam call                            |
| Result unwrapping        | `unwrapGleamResult()` for Gleam's `Ok`/`Error` types          |

### What is NOT Pi's concern (Gleam's job)

- How `task.add()` works internally → pure Gleam
- SQL queries → pure Gleam  
- Database connections → pure Gleam
- Business logic → pure Gleam
- Type safety → pure Gleam

### Key insight: The boundary is THIN

```
┌─────────────────────────────────────────┐
│  extension.js (generated by Gleam)       │
│  ┌───────────────────────────────────┐  │
│  │  import { task_add } from gleam   │  │  ← JS imports Gleam-compiled .mjs
│  │  pi.registerTool({                │  │
│  │    execute(id, params, _, _, ctx) │  │  ← Pi API contract
│  │      const r = await task_add(...) │  │  ← calls into Gleam
│  │      return unwrap(r)             │  │  ← converts Gleam→JS
│  │  })                               │  │
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘
         ↑ thin JS layer (Pi's requirement)
         ↓
┌─────────────────────────────────────────┐
│  Gleam modules (pure Gleam)              │
│  task.gleam, issue.gleam, broadcast...  │  ← all business logic here
└─────────────────────────────────────────┘
```
